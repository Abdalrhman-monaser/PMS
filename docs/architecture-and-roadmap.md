# الهيكلية التفصيلية لنظام PMS وخارطة طريق التطوير

**النسخة الحالية:** v1.0 (PHP + MySQL, بيئة XAMPP محلية)
**الحالة:** نظام يعمل فعليًا — CRUD كامل للمشاريع/المهام/الفريق + مصادقة + لوحة تحكم

---

## 1.: الهيكلية المعمارية العامة

النظام مبني على نمط **MVC مبسّط بدون إطار عمل (Framework-less)**، مقسّم لطبقات واضحة المسؤولية:

```
┌─────────────────────────────────────────────────────┐
│  طبقة العرض (Presentation)                            │
│  modules/*/index.php, edit.php, view.php              │
│  + includes/header.php, footer.php  (القالب المشترك)   │
└───────────────────────┬─────────────────────────────┘
                         │
┌───────────────────────▼─────────────────────────────┐
│  طبقة المنطق المشترك (Shared Logic / Helpers)          │
│  includes/helpers.php   → e(), url(), csrf, badges     │
│  includes/auth.php      → login/logout/role guards     │
└───────────────────────┬─────────────────────────────┘
                         │
┌───────────────────────▼─────────────────────────────┐
│  طبقة الوصول للبيانات (Data Access)                    │
│  config/database.php   → PDO singleton (db())          │
│  استعلامات SQL مباشرة داخل كل صفحة (prepared statements)│
└───────────────────────┬─────────────────────────────┘
                         │
┌───────────────────────▼─────────────────────────────┐
│  قاعدة البيانات (MySQL — pms_db)                       │
│  database/schema.sql                                   │
└─────────────────────────────────────────────────────┘
```

**ملاحظة هندسية مهمة:** لا يوجد حاليًا طبقة "Repository" أو "Model" منفصلة — كل صفحة تكتب استعلاماتها مباشرة عبر `db()`. هذا مقصود لإبقاء v1 بسيطًا وسريع الفهم لمشروع محلي بحجم صغير-متوسط. في المرحلة 4 أدناه سنعيد الهيكلة نحو طبقة Repository حقيقية عندما يكبر عدد الاستعلامات المكررة.

## 3. مخطط قاعدة البيانات (ERD منطقي)

```
users ──────────────┬──────────────────────────────┐
  │ id (PK)          │                               │
  │ role             │ owner_id / created_by         │ assigned_to / reviewer_id
  │ ...              ▼                               ▼
  │              projects ◄──────────┐            tasks ◄──────────┐
  │              │ id (PK)           │            │ id (PK)         │
  │              │ code (UNIQUE)     │            │ project_id (FK) │
  │              │ status            │ project_id │ phase_id (FK)   │
  │              │ progress          │            │ parent_task_id ─┘ (self-FK لـ subtasks)
  │              └──────┬────────────┘            │ status/priority │
  │                     │                          │ progress        │
  │                     ▼                          └──────┬──────────┘
  │                  phases                                │
  │              │ id (PK)                                 ├──► task_comments
  │              │ project_id (FK)                          │      (user_id FK → users)
  │              │ sequence_order                            │
  │              └───────────────────────                    ├──► task_dependencies
  │                                                            │      (task_id ↔ depends_on_task_id)
  └──► project_members (جدول ربط M:N بين users و projects)     │
         │ project_id (FK), user_id (FK), role_in_project      └──► attachments
                                                                        (task_id/project_id FK)

activity_log  →  سجل تدقيق مستقل (user_id FK) يُغذّى من logActivity() في كل عملية إنشاء/تعديل
```

**جداول موجودة في المخطط لكن بدون واجهة بعد** (البنية جاهزة، تنتظر شاشات):
- `attachments` — رفع الملفات
- `task_dependencies` — علاقات "تعتمد على" بين المهام

## 4. خارطة طريق التطوير (Development Roadmap)

بناءً على النظام الحالي، هذه هي المراحل المقترحة بالترتيب — كل مرحلة تُبنى فوق سابقتها ولا تكسر شيئًا موجودًا.

### المرحلة 2 — إغلاق الفجوات الوظيفية الأساسية
الهدف: استغلال الجداول الجاهزة في قاعدة البيانات التي لا واجهة لها بعد.

| # | المهمة | التفاصيل | الجداول المستخدمة |
|---|--------|----------|---------------------|
| 2.1 | رفع المرفقات | نموذج رفع ملف في `tasks/view.php` و `projects/view.php`، تخزين فعلي في `/uploads/` خارج `htdocs` أو محمي، وربط بجدول `attachments` | `attachments` |
| 2.2 | تبعيات المهام | واجهة "تعتمد هذه المهمة على" داخل `tasks/edit.php` + تحذير بصري في `view.php` لو التبعية غير مكتملة | `task_dependencies` |
| 2.3 | حذف ناعم فعلي (Soft Delete) | إضافة أزرار حذف فعلية في القوائم (حاليًا `deleted_at` موجود بالمخطط لكن غير مُستخدم في أي واجهة) | `projects`, `tasks`, `users` |
| 2.4 | صفحة "المهام الخاصة بي" | فلترة سريعة لمهام المستخدم الحالي من الشريط الجانبي | `tasks` |

**مخرجات المرحلة:** لا جداول جديدة، فقط واجهات لما هو موجود فعليًا.

---

### المرحلة 3 — التقارير والتحليلات (Dashboard متقدم)
الهدف: تحويل البيانات المتراكمة إلى رؤى قابلة للقراءة بصريًا.

| # | المهمة | التفاصيل |
|---|--------|----------|
| 3.1 | مخطط Gantt | صفحة `modules/reports/gantt.php` تعرض المهام كخط زمني (Canvas/SVG بسيط بدون مكتبات خارجية ثقيلة) |
| 3.2 | Burndown Chart | لكل مشروع: تتبع المهام المتبقية يوميًا عبر استعلام على `activity_log` و `tasks.completed_at` |
| 3.3 | تقرير أداء الفريق | صفحة تجمع: معدل إنجاز المهام، متوسط الوقت الفعلي مقابل المقدّر (`actual_hours` عمود يحتاج إضافة تحديثه من واجهة `tasks/edit.php`) |
| 3.4 | تصدير PDF/Excel | تصدير أي تقرير كملف — يحتاج مكتبة PHP خارجية (مثل TCPDF أو PhpSpreadsheet عبر Composer) |

**قرار هندسي مطلوب هنا:** إدخال Composer لأول مرة (لمكتبات PDF/Excel) — سيغيّر بنية المشروع قليلاً (`vendor/` + `composer.json`). سنناقشه عند الوصول لهذه المرحلة.

---

### المرحلة 4 — إعادة هيكلة الطبقة الوسطى (Refactor)
الهدف: تقليل تكرار كود SQL المتناثر في كل صفحة، قبل أن يكبر المشروع أكثر.

| # | المهمة | التفاصيل |
|---|--------|----------|
| 4.1 | طبقة Repository | إنشاء `includes/repositories/ProjectRepository.php`, `TaskRepository.php`, إلخ — تُغلّف كل استعلامات SQL المتكررة (find, create, update) |
| 4.2 | طبقة Validation موحّدة | دالة `validate()` عامة بدل تكرار `if ($x === '')` يدويًا في كل `edit.php` |
| 4.3 | فصل العرض عن المنطق أكثر | نقل استعلامات كل صفحة `view.php`/`index.php` لتستدعي الـ Repository بدل `$pdo->query()` المباشر |

**هذه المرحلة لا تضيف ميزات جديدة للمستخدم — هدفها صيانة أسهل مستقبلًا.**

---

### المرحلة 5 — الصلاحيات التفصيلية (Fine-grained Permissions)
حاليًا: 3 أدوار فقط (admin/manager/member) بصلاحيات ثابتة في الكود (`requireRole()`).

| # | المهمة | التفاصيل |
|---|--------|----------|
| 5.1 | جدول `permissions` + `role_permissions` | صلاحيات قابلة للتخصيص بدل الترميز الثابت |
| 5.2 | صلاحيات على مستوى المشروع | مثال: عضو يرى مشروعًا واحدًا فقط بدل كل المشاريع |
| 5.3 | واجهة إدارة الصلاحيات | شاشة للأدمن لتعديل من يقدر يفعل ماذا |

---

### المرحلة 6 — الإشعارات والتنبيهات:
| # | المهمة | التفاصيل |
|---|--------|----------|
| 6.1 | جدول `notifications` | إشعار داخل النظام عند: تعيين مهمة، اقتراب موعد استحقاق، تعليق جديد |
| 6.2 | جرس إشعارات في `header.php` | عداد + قائمة منسدلة |
| 6.3 | (اختياري) بريد إلكتروني | عبر PHPMailer + SMTP محلي أو خدمة خارجية |

---

### المرحلة 7 — الجاهزية للإنتاج (Production Readiness)
عند الرغبة بنقل النظام من XAMPP المحلي لاستضافة حقيقية:

| # | المهمة | التفاصيل |
|---|--------|----------|
| 7.1 | متغيرات بيئة | نقل بيانات الاتصال من `config/database.php` إلى ملف `.env` غير مرفوع لـ Git |
| 7.2 | HTTPS + إعدادات أمان الجلسة | `session.cookie_secure`, `cookie_httponly`, `SameSite` |
| 7.3 | نسخ احتياطي تلقائي لقاعدة البيانات | Cron job لـ `mysqldump` دوري |
| 7.4 | تسجيل الأخطاء (Logging) | توجيه أخطاء PHP لملف log بدل عرضها للمستخدم |
| 7.5 | اختبار الحمل | التأكد من أداء الاستعلامات عند نمو البيانات (مراجعة الفهارس الحالية) |

## 5. ترتيب الأولوية المقترح

```
المرحلة 2 (إغلاق الفجوات)  →  الأكثر فائدة فورية، بدون مخاطر هيكلية
        │
المرحلة 3 (تقارير)         →  قيمة عالية للإدارة، مستقلة عن باقي المراحل
        │
المرحلة 4 (Refactor)       →  استثمار تقني، يُفضّل قبل ما يكبر الكود أكثر
        │
المرحلة 5 (صلاحيات) ┬ المرحلة 6 (إشعارات)   →  يمكن تنفيذهما بالتوازي، مستقلتان عن بعض
        │
المرحلة 7 (إنتاج)          →  فقط عند القرار بالنشر خارج XAMPP المحلي
```

## 6. ملاحظة ختامية

كل مرحلة أعلاه مصممة لتُبنى **فوق** الكود الحالي دون كسره — لا توجد إعادة كتابة جذرية مطلوبة في أي مرحلة إلا المرحلة 4 (وحتى هي تدريجية، ملف تلو الآخر). يمكن تنفيذ أي مرحلة بشكل منفصل حسب أولويتك.

أخبرني بأي مرحلة تريد البدء فيها وسأبني الكود الفعلي لها مباشرة.
